# Память и длительный разговор

## Текущее поведение

Каждое сообщение вызывает новый `run_agent`, но **не создаёт новый FrameStore** в исправной сессии Gradio. Таблицы и логин SuperMAG остаются на сервере в состоянии этой браузерной сессии. В новую модельную беседу добавляется сводка последних четырёх пар реплик: до 300 символов из каждой реплики и до 12 имён таблиц.

Внутри одного `run_agent` работает отдельный Scratchpad: текущая таблица, реестр полученных handle, завершённые шаги, краткие численные результаты и ошибки. Старые tool-exchanges вытесняются целиком. Scratchpad заново создаётся при следующем сообщении; все прежние численные выводы не становятся долговременной памятью автоматически.

Поэтому неверны оба крайних утверждения: «каждое сообщение полностью забывает всё» и «агент помнит весь многолетний диалог». У него есть память данных внутри сессии и ограниченный текстовый контекст.

## Что проверено

Локальная HTTP-проверка провела 14 последовательных сообщений: загрузка → график → 12 статистических обращений к прежней таблице. Таблица сохранилась. В независимой HTTP-сессии этот handle не разрешился. Браузер показал график после загрузки в предыдущем сообщении.

Это проверяет серверное состояние и передачу сообщений. В роли модели был детерминированный TestBrain; результат не подтверждает, что Qwen правильно поймёт местоимение «тот» через двадцать ходов.

## Границы и риск для пользователей

- После вытеснения давнего текста могут потеряться цель исследования, договорённости о станции/единицах и смысл «предыдущего графика».
- Список handle выбирается из отсортированных имён; последние 12 в этом списке не обязательно самые свежие или подходящие запросу.
- Данные живут в RAM без общего ограничения объёма. Много станций/дней увеличивают память процесса.
- После перезапуска сервера таблицы автоматически не восстанавливаются из CSV проекта. Нет durable conversation/session store.
- Сохранённые проекты и exports сейчас общие на диске; независимость таблиц не равна tenant isolation SaaS.
- Новый FrameStore в запасном пути UI теперь получает собственный Workspace, поэтому указатель активного проекта не наследуется от другой такой сессии. Это не разделяет общий файловый каталог по владельцам.
- Встроенная очистка transcript Gradio не является доказанным полным удалением таблиц/артефактов. Для записи независимого опыта нужна новая браузерная сессия или перезапуск тестового приложения.

Для MVP ограниченный контекст допустим, если поведение ясно и воспроизводимо. Выдавать его за готовый ассистент для неограниченной долгой работы нельзя. Для SaaS этот раздел требует отдельного этапа: цели и параметры исследования в структурированном состоянии, выбор актуальных handle, bounded память, сохранение/восстановление сессии и изоляция пользователей.

## Живая приёмка Qwen: 20 ходов

В той же Gradio-сессии, без ручного исправления результатов. Ниже — прежний план проверки, а готовые сообщения для копирования приведены после него. Строку «6–12» нельзя отправлять одним сообщением: это несколько отдельных ходов.

1. Загрузить IRT 2024-09-10, H/D/I, график H. Сохранить точный handle и медиану H из инструмента.
2. «Теперь D из тех же данных, не скачивай повторно».
3. «Посчитай медиану H для того же дня»; сверить с инструментом, не с воспоминанием модели.
4. Загрузить IRT 2024-09-11 и сравнить два дня; разные handle и две кривые.
5. Загрузить BOU за 2024-09-10; явно сменить рабочую станцию.
6–12. Поочерёдно статистика X/Y/Z/F/H и графики для BOU с явной датой. Не просить запоминать прежние числа.
13. «Вернись к самому первому дню IRT. Построй H без новой загрузки». Если контекст неоднозначен, уточнение считается корректным; выдуманный день — провал.
14. Явно указать первый handle; повторить тот же запрос. Таблица обязана существовать.
15. Получить Kp/Dst из Kyoto за первый день.
16. Получить OMNI за первый день.
17. Сопоставить H первой IRT с Bz/V, проверить время и подписи.
18. Передать заведомо неизвестный handle и попросить объяснить ошибку.
19. Вернуться к корректному handle и построить график.
20. Попросить краткую сводку с использованными станциями/датами/файлами. Сверить с журналом и диском.

Критерии: нет подмены станции/даты; при явном handle нет повторной загрузки без причины; ошибки не превращаются в выдуманные числа; после отказа следующий корректный запрос работает. Отдельная сессия B должна не видеть таблицы A. Для семантики давнего местоимения принимается уточнение, а не угадывание.

Если живой пункт 13 ошибается, а 14 работает, ремонтировать нужно выбор контекста, а не таблицы или загрузчик. Если 14 теряет frame — это дефект серверного состояния; видео о длинном диалоге до исправления не записывать как успешное.

## Сообщения для копирования: по одному на ход

Перед проверкой записать HEAD, версии и время. Для каждого ответа сохранить «Журнал инструментов»: текст ответа сам по себе не доказывает отсутствие повторного fetch, правильные числа или две кривые. Следующие блоки копировать отдельно, без заголовков и критериев.

1. Первый день IRT:
```text
Загрузи INTERMAGNET IRT за 2024-09-10. Рассчитай H/D/I, получи статистику H инструментом и построй график H. Укажи точный handle и медиану H.
```
2. Продолжение:
```text
Теперь построй D из тех же данных и получи его медиану инструментом. Не скачивай данные повторно.
```
3. Повторная статистика:
```text
Посчитай медиану H для того же дня через инструмент, без новой загрузки.
```
4. Две даты:
```text
Загрузи IRT за 2024-09-11, рассчитай H и сравни с IRT за 2024-09-10 на одном графике H. Нужны две подписанные кривые и разные handle для двух дней.
```
5. Смена станции:
```text
Переключись на BOU: загрузи INTERMAGNET за 2024-09-10 и рассчитай H/D/I. Укажи handle BOU.
```
6. X:
```text
Получи инструментом статистику X для BOU за 2024-09-10, без повторной загрузки.
```
7. Y:
```text
Получи инструментом статистику Y для BOU за 2024-09-10, без повторной загрузки.
```
8. Z:
```text
Получи инструментом статистику Z для BOU за 2024-09-10, без повторной загрузки.
```
9. F:
```text
Получи инструментом статистику F для BOU за 2024-09-10, без повторной загрузки.
```
10. H:
```text
Получи инструментом статистику H для BOU за 2024-09-10, без повторной загрузки.
```
11. Вектор:
```text
Построй X/Y/Z для BOU за 2024-09-10 из уже загруженных данных.
```
12. H и F:
```text
Построй H и F для BOU за 2024-09-10 из уже загруженных данных.
```
13. Давняя ссылка:
```text
Вернись к самому первому дню IRT в этом разговоре. Построй H без новой загрузки. Если дата уже не видна в контексте, уточни её.
```
14. Явный handle:
```text
Используй derived:irt:2024-09-10. Построй H без скачивания и повторного расчёта H/D/I.
```
15. Kyoto:
```text
Получи индексы Kyoto Dst/Kp за 2024-09-10. Рассчитай их статистику инструментом и построй график с отдельными шкалами: Dst в nT, Kp безразмерный. Укажи handle.
```
16. OMNI:
```text
Загрузи солнечный ветер OMNI за 2024-09-10. Укажи точный handle и число строк.
```
17. Сопоставление:
```text
Сопоставь H из derived:irt:2024-09-10 с Bz и V из sw:omni:2024-09-10. Используй уже загруженные таблицы, построй график сравнения земли и солнечного ветра.
```
18. Отрицательный пример:
```text
Получи статистику H из raw:zzz:1900-01-01. Это проверка неизвестного handle: не загружай замену и не придумывай значения; сообщи причину отказа.
```
19. Восстановление:
```text
Теперь получи статистику H и построй H из derived:irt:2024-09-10. Без новой загрузки.
```
20. Граница памяти:
```text
Кратко перечисли станции, даты и результаты, которые можешь подтвердить доступным контекстом и инструментами. Не восстанавливай забытые числа по догадке; явно укажи пробелы.
```

Критерии прежние: сверить каждый численный ответ с журналом, графики открыть и проверить их данные/подписи; в ходах без загрузки не должно быть fetch. В ходе 13 корректное уточнение допустимо. В ходе 20 отсутствие полного архива беседы нужно признать, а не заполнить догадками. Не использовать набор как доказательство неограниченной памяти или полного покрытия продукта.

## Присланный живой опыт 02.11.2026

На 3bca4a1 пользователь получил несколько продолжений IRT/BOU и затем повторяющийся отказ Kyoto: unknown_component для DST/KP, один tool_not_available для незапрошенного графика, около 500 секунд до ответа. Это FAIL данного сценария. Семь сообщений, включая объединённые пункты, не считаются двадцатью ходами. Числа BOU из итогового текста пока не сверены с журналом; F не согласуется с указанными диапазонами X/Y/Z и требует отдельной проверки исходных значений и ответа модели.

Исправление статистики разрешает реальные имена колонок без учёта регистра, сохраняет единицы Dst/Kp и отклоняет неоднозначные совпадения. Повтор одной неуспешной операции ограничен шестью попытками в run_agent; это ограничение повторов, не гарантия времени ответа. Неуспешная статистика больше не считается восстановленной только потому, что загрузка прошла или в ответе есть имя HTML. Повтор с настоящей Qwen после публикации исправления остаётся обязательным.

В следующем присланном диалоге (после публикации 568bb98, точный HEAD сессии в приложении не указан) ответ Kyoto уже содержал статистику и один зарегистрированный график. BOU дал два графика, последующие обращения к IRT — по одному. Последний ответ на «Сопоставить H первой IRT с Bz/V, проверить время и подписи» перечислил три файла без штатного итога построения. Журнал последнего запроса не предоставлен; перечисление файлов моделью не доказывает их существования.

В коде воспроизведены причины, мешающие этому сценарию: router не распознавал такое сопоставление и не предлагал plot_space_weather_comparison; Gradio передавал для маршрутизации историю вместе с текущим вопросом, и старые темы занимали ограниченный набор инструментов. Теперь Gradio передаёт отдельный routing_query для текущего сообщения, сохраняя сводку истории в запросе модели. Сопоставление наземного H с Bz/солнечным ветром получает обязательные инструменты двух источников и специализированного графика. Если модель завершает его без успешного построения, следуют до двух корректирующих обращений, затем явный plot_not_built вместо выдуманного списка файлов. Это проверка данного вида сравнения, не универсальная верификация всего текста модели.

Ошибка calculate_derived_components с ['F'] относится к отдельной неверной попытке модели: инструмент рассчитывает H/D/I, а имеющуюся F нужно читать из таблицы. Она не доказывает общего отказа построения. Запрос только на загрузку OMNI не обязывает строить график. Для полной приёмки по-прежнему нужны журналы и открытые артефакты настоящего запуска.
