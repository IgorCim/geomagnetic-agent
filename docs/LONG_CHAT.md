# Память и длительный разговор

## Текущее поведение

Каждое сообщение вызывает новый `run_agent`, но **не создаёт новый FrameStore** в исправной сессии Gradio. Таблицы и логин SuperMAG остаются на сервере в состоянии этой браузерной сессии. В модельную беседу добавляется сводка последних четырёх пар реплик: до 300 символов из каждой реплики и до 12 имён таблиц, с приоритетом реально использованных недавно таблиц.

После ремонта 03.11.2026 FrameStore также хранит SessionMemory: первую успешно полученную таблицу, до 128 первых наземных загрузок в порядке выполнения, до 12 недавно использованных таблиц и входы последней успешной операции. Эти факты обновляются по успешным результатам инструментов, а не по тексту модели. «Первый день» разрешается по первой подтверждённой таблице; «первый день IRT» — по первой подтверждённой загрузке IRT. Если данных для такого вывода нет либо предыдущая операция использовала несколько таблиц и ссылка неоднозначна, приложение просит уточнение.

Для одиночных запросов Gradio передаёт в run_agent проверяемые условия: распознанную ISO-дату, станцию, явный handle, запрет повторной загрузки и ожидаемые результаты. Подмена распознанной даты/станции/таблицы блокируется до соответствующего обработчика. При пропущенной загрузке, статистике или графике модель получает до двух уточняющих обращений, затем явный неполный результат. Для простых запросов загрузки/статистики/графиков итог собирается из реальных результатов; произвольные численные утверждения модели в этот итог не переносятся. Сводка таблиц и зарегистрированных файлов строится приложением с проверкой существования файлов.

Внутри одного `run_agent` работает отдельный Scratchpad: текущая таблица, реестр полученных handle, завершённые шаги, краткие численные результаты и ошибки. Старые tool-exchanges вытесняются целиком. Scratchpad заново создаётся при следующем сообщении; все прежние численные выводы не становятся долговременной памятью автоматически.

Поэтому неверны оба крайних утверждения: «каждое сообщение полностью забывает всё» и «агент помнит весь многолетний диалог». У него есть память данных внутри сессии и ограниченный текстовый контекст.

## Что проверено

Локальная HTTP-проверка провела 14 последовательных сообщений: загрузка → график → 12 статистических обращений к прежней таблице. Таблица сохранилась. В независимой HTTP-сессии этот handle не разрешился. Браузер показал график после загрузки в предыдущем сообщении.

Это проверяет серверное состояние и передачу сообщений. В роли модели был детерминированный TestBrain; результат не подтверждает, что Qwen правильно поймёт местоимение «тот» через двадцать ходов.

## Границы и риск для пользователей

- После вытеснения давнего текста могут потеряться цель исследования, договорённости о станции/единицах и смысл «предыдущего графика».
- Пересказ текста ограничен четырьмя парами; структурированные факты сохраняют опорные данные, но не все договорённости или смысл произвольного научного разговора. Двенадцать handle не покрывают все данные большой сессии.
- Данные живут в RAM без общего ограничения объёма. Много станций/дней увеличивают память процесса.
- После перезапуска сервера таблицы автоматически не восстанавливаются из CSV проекта. Нет durable conversation/session store.
- Сохранённые проекты и exports сейчас общие на диске; независимость таблиц не равна tenant isolation SaaS.
- Новый FrameStore в запасном пути UI теперь получает собственный Workspace, поэтому указатель активного проекта не наследуется от другой такой сессии. Это не разделяет общий файловый каталог по владельцам.
- Кнопка «Новый диалог» очищает transcript, список показанных файлов, таблицы и факты этой сессии. Файлы на диске сохраняются. Это не удаление данных проекта и не изоляция общих файлов по пользователям.

Новые проверки условий подключены к одиночным запросам Gradio. Прямой Python-вызов run_agent без contract, массовый planner и произвольные научные интерпретации не получают универсальной проверки всех утверждений. Разрешение естественного языка ограничено распознаваемыми формами: это не гарантия правильности любого запроса. [Ремонт и его границы](CHAT_REPAIR_20261103.md).

Для MVP ограниченный контекст допустим, если поведение ясно и воспроизводимо. Выдавать его за готовый ассистент для неограниченной долгой работы нельзя. Для SaaS этот раздел требует отдельного этапа: цели и параметры исследования в структурированном состоянии, выбор актуальных handle, bounded память, сохранение/восстановление сессии и изоляция пользователей.

## Живая приёмка Qwen: 20 отдельных сообщений

**Живой beff60b: частичный результат / FAIL всего сценария.** Графики зарегистрированы, но статистика BOU X/Y/Z/F и последняя сводка не прошли. Последующее исправление привязки компонентов и формулировок сводки проверено локально; его живая приёмка — LIVE_PENDING. [Присланный запуск, доказательства и следующий короткий тест](LIVE_BEFF60B_20261103.md). Более ранний разбор: [5dcb3b9](LONG_CHAT_FAILURE_20261102.md), [первый ремонт](CHAT_REPAIR_20261103.md).

Прежний план с объединённой строкой «6–12» удалён: он выглядел как 13 сообщений и содержал инструкции проверяющему. Ниже единственный набор из двадцати отдельных сообщений. Критерии: не подменять дату/станцию; не загружать заново при явном handle без причины; не выдумывать числа после ошибки; после отказа корректный запрос должен работать. Для неоднозначной ссылки правильный исход — уточнение. В независимой браузерной сессии таблицы первой сессии недоступны.

Перед проверкой записать HEAD, версии и время. Для каждого ответа сохранить «Журнал инструментов»: текст ответа сам по себе не доказывает отсутствие повторного fetch, правильные числа или две кривые. Следующие блоки копировать отдельно, без заголовков и критериев.

## Присланный живой опыт 02.11.2026

На 3bca4a1 пользователь получил несколько продолжений IRT/BOU и затем повторяющийся отказ Kyoto: unknown_component для DST/KP, один tool_not_available для незапрошенного графика, около 500 секунд до ответа. Это FAIL данного сценария. Семь сообщений, включая объединённые пункты, не считаются двадцатью ходами. Числа BOU из итогового текста пока не сверены с журналом; F не согласуется с указанными диапазонами X/Y/Z и требует отдельной проверки исходных значений и ответа модели.

Исправление статистики разрешает реальные имена колонок без учёта регистра, сохраняет единицы Dst/Kp и отклоняет неоднозначные совпадения. Повтор одной неуспешной операции ограничен шестью попытками в run_agent; это ограничение повторов, не гарантия времени ответа. Неуспешная статистика больше не считается восстановленной только потому, что загрузка прошла или в ответе есть имя HTML. Повтор с настоящей Qwen после публикации исправления остаётся обязательным.

В следующем присланном диалоге (после публикации 568bb98, точный HEAD сессии в приложении не указан) ответ Kyoto уже содержал статистику и один зарегистрированный график. BOU дал два графика, последующие обращения к IRT — по одному. Последний ответ на «Сопоставить H первой IRT с Bz/V, проверить время и подписи» перечислил три файла без штатного итога построения. Журнал последнего запроса не предоставлен; перечисление файлов моделью не доказывает их существования.

В коде воспроизведены причины, мешающие этому сценарию: router не распознавал такое сопоставление и не предлагал plot_space_weather_comparison; Gradio передавал для маршрутизации историю вместе с текущим вопросом, и старые темы занимали ограниченный набор инструментов. Теперь Gradio передаёт отдельный routing_query для текущего сообщения, сохраняя сводку истории в запросе модели. Сопоставление наземного H с Bz/солнечным ветром получает обязательные инструменты двух источников и специализированного графика. Если модель завершает его без успешного построения, следуют до двух корректирующих обращений, затем явный plot_not_built вместо выдуманного списка файлов. Это проверка данного вида сравнения, не универсальная верификация всего текста модели.

Ошибка calculate_derived_components с ['F'] относится к отдельной неверной попытке модели: инструмент рассчитывает H/D/I, а имеющуюся F нужно читать из таблицы. Она не доказывает общего отказа построения. Запрос только на загрузку OMNI не обязывает строить график. Для полной приёмки по-прежнему нужны журналы и открытые артефакты настоящего запуска.
